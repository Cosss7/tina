### 2.3 议题二 · 架构设计（讨论中）

已定：

- **单一写者**：家节点写日志，其余 attach；家可迁移（D16）
- **进程边界**：引擎跑在独立进程，靠端口驱动（D18）

**Router 的能力模型**（对 D17 的细化，取代"8 种意图"的说法）：

| 能力等级 | 例子 | 形态 | 理由 |
|---|---|---|---|
| **只读** | 看板、任务历史、项目约定、记忆检索 | 工具 | 无副作用，越方便越好 |
| **低风险副作用** | 发消息、建卡、改状态 | 工具（过策略） | 可撤销、影响面小 |
| **高风险副作用** | 改文件、跑命令、开 PR、调外部 API | **只能是意图** | 由运行时执行，策略/预算/审计都在这条路上 |

核心原则：**手里的工具不能"改世界"，只能"表达"。**

由此带来的架构后果：意图集是**开放的**（注册表），所以执行管道必须统一——**所有意图走同一条「校验 → 执行 → 审计」的路**，否则每加一个意图就要改一遍管道。

**任务模型**（D19 / D20）：

- 任务平铺，不做任务树；任务之间用依赖（`blockedBy`）表达先后
- 一个任务可以挂多个 worker（数据模型 1:N），v1 只实现单 worker
- 卡片内部可以有"步骤"，但不单独占看板

**完成判定**（D21，暂定）：Worker 交报告 → 卡进"评审中" → Router 首审（可派 reviewer worker 做对抗性检查）→ 人终审 → "已完成"；按自主度可跳过一级，L3 可跳过人的终审。

### 2.4 增补（2026-11-06，对照 Super-agent 与 multica）

读了两份材料：DeepSeek Harness 团队的[《Super-agent 设计探索》](https://telegra.ph/Super-agent-%E8%AE%BE%E8%AE%A1%E6%8E%A2%E7%B4%A2%E8%BF%88%E5%90%91%E6%9B%B4%E8%87%AA%E4%B8%BB%E7%9A%84-Agent-%E7%B3%BB%E7%BB%9F-10-31-2)，以及开源项目 multica（看板 + agent 当负责人 + 本机 daemon 的成熟实现，9 个月 5969 次提交）。

| # | 结论 | 依据 |
|---|---|---|
| D40 | 事件先过程序快路径，三态（处理 / 忽略 / 说不清）；说不清的才进 Router；已归属任务的事件直投执行者 | 文章的 Fast / Slow Path；它测出去掉直通后 Router 决策 +30%、token +37%，完成时间不变 |
| D41 | Worker 接入只有一条：节点注册；个人 agent 与团队 agent 的差别在节点归属 | multica 的 runtime 模型——所有执行都由 daemon 领取，没有"控制面托管"分支 |
| D42 | 每个 Run 有发起人；共享 agent 的动作代表调用者 | multica 的运行令牌绑定用户 + 评论里"创建（代表某人）" |
| D43 | 跨项目没有 agent，只有视图 | 文章没有项目概念（一个全局 Router），multica 的项目只是容器——两边都没有跨项目协调者 |
| D44 | Router 的记忆是显式对象，不是"会话还开着" | 文章用常驻会话换连续性，multica 每次 run 重建上下文；这是中间的第三条路 |
| D45 | 节点权限：家跟项目成员、执行跟所有者；管理员没有使用权 | multica 的运行时默认私有，"只有运行时所有者可以在它上面创建智能体，工作区的 owner、admin 也不例外" |

由这两份材料反证出来的三条：

1. **"Router 不亲手干"是三方独立收敛的结论**——文章说 Router 甚至可以不配 Bash，multica 的队长"派完活就停"。这不是我们的偏好，是结构上的必然。
2. **沙箱不是 Worker 的定义属性，是部署形态的属性**。H0 没有沙箱，Worker 就是用户机器上的 dsh；边界是那个用户的操作系统权限。
3. **事件语义的正确性吃掉大部分工程量**。multica 用一份 42KB 的工程文档加十几个迁移，处理回执消费、去重合并、自触发抑制、滚动升级期间的兼容。我们目前只有一张事件表——这是被低估得最多的一块。

## 4. 判断集

**J1 · 单人起步的坑：不要把产品做成个人效率工具。**
单人用户的痛决定"先做什么"，团队协作的形态决定"怎么建"。单人阶段也必须坚持事件、看板、结构化回报、隔离执行。

**J2 · 单人卖编排，团队卖协作。**
共享同一套底层，主打语不同。

**J3 · 会话可弃，是架构的分水岭。**
"会话一关就没了"的东西都不是产品资产。推论：回报协议、双日志、引擎端口。

**J4 · 方法可以被替换，问题不能被替换。**
讨论围绕"要不要做多智能体"而不是"哪个子问题没解决"时，就是跑偏了。

**J5 · 问题必须带着用途。**
被反感的不是"问得多"，是"答完不知道改变了什么"。每个问题都要能说出：它决定文档哪一段、两种答案对应哪两种写法。

**J6 · 限制手，不限制脑。**
智能体的自由应该体现在"想"（拆解、排序、选择），而不是"手"（改文件、执行命令）。凡是能改世界的能力，都必须经过运行时。

**J7 · 控制面不参与 agent 的决策链。**
Router 管"做什么"，控制面管"找得到"。两者从不直接通信：Router 只产出意图，运行时去执行；控制面只搬字节与维护摘要。
判断两者是否被混淆，用一个思想实验：**控制面挂了，工作继续、只是看不见；Router 挂了，工作停、但看得见。** 两个故障互不传染。
