# H0 验收报告

> 2026-11-06 · 对应 `docs/h0.md` 第 2 节的四条验收。
> 这一版是脚手架，不是产品：它的成功不看好不好用，看两个问题有没有答案。

## 一、四条验收

| # | 动作 | 结果 |
|---|---|---|
| 1 | `tina up` | ✅ `make up` 一条命令起控制面与节点，`http://127.0.0.1:7801` 上是两个项目的四列看板；杀掉节点后头部在 1 秒内显示"节点离线" |
| 2 | `demo.sh` | ✅ 从空库跑到"卡片进已完成"，六步状态逐条打在终端上 |
| 3 | `make verify` | ✅ 前端构建 + 控制面构建 + 类型检查 + `go test` + `node --test`，32 条测试；不访问网络、不调真实模型 |
| 4 | 手工 demo（真 dsh） | ✅ 同一套闭环，引擎换成真 dsh 跑通：真模型出计划、三张卡各跑一轮、报告落库、人终审 |

第 4 条的跑法（不写绝对路径，按本机实际的 dsh 位置填）：

```bash
export TINA_ENGINE_BIN=<仓库>/packages/engine-dsh/src/bin.ts
export TINA_DSH_BIN=<dsh 安装位置>/@deepseek-ai/dsh/lib/bin.js
export TINA_WORK_DIR=<一个空目录>
export DSH_HOME=<隔离的 dsh home>
bash demo.sh
```

`TINA_DSH_REASONING=off` 是默认值：H0 要的是稳定的结构化输出，不是思考。把它打开后实测模型会用光输出预算、只写思考，正文一个字不剩。

## 二、两个问题

### 1. vision 3.5 的待验证项，H0 之后还剩几个没答？

五条里答了一条。

| 待验证 | 状态 |
|---|---|
| bridge 插件能否做到 cancel / fork / list | **答了**：cancel 在进程内可行（`agent.cancel`），fork 只能从已落盘的日志前缀切，list 无所谓。协议层没有这三样，M0.1 实测确认 |
| SQLite 在多人 attach + 高频事件下的写性能 | 没答。H0 是单用户单写者，压测放到 v1 |
| Effect 与子进程 / 流的集成复杂度 | 没答，**而且绕开了**：H0 的节点运行时是普通 async，没上 Effect（见决策记录 D63） |
| WS 中继的延迟 | 没答。H0 只有本机 loopback |
| Electron 的打包体积与启动时间 | 没答。H0 不做桌面 |

结论：**三个待验证问题里，只有"引擎能不能被正确驱动"这一条真的被 H0 回答了**，其余四条都要等有真实用户和真实网络条件。

### 2. 引擎端口的协议，H0 之后要不要推倒重来？

**不用，但要补一层。**

端口本身站住了：七种事件、八个方法，把 fake engine 和真 dsh 都装进去了。真 dsh 那侧要改的只有 `packages/engine-dsh` 一个包，产品侧一行没动——这正是 vision 2.8 说的"端口是防波堤"。

要补的是**打断的粒度**。现在 `interrupt` 等于关进程（D48/D49）：一个会话一个 dsh 进程，打断就是让它退出，下一次 `send` 前重新拉起并 `session/resume`，代价约 1.8 秒。够用，但 v1 要支持"停掉一个正在跑的 Run，Router 不受影响"时，就得在 `tina-node` profile 里加插件，把 `agent.cancel({kind:'user'})` 接到 `session/interrupt` 上。端口的形状不用动，换的是实现。

## 三、范围表没兑现的五处

验收四条全过，但 `h0.md` 第 3 节「做」那张表逐行对下来，有五处没建（细节见决策记录 D64）：

| 范围表写的 | 实际 | 什么时候还 |
|---|---|---|
| 控制面的摘要索引 | 没做，控制面不存任务（D58） | 等"节点离线也要看看板"成为真需求 |
| 节点的事件收件箱与调度 | 没做，一条同步链路，没有队列 | 等有并发和重试 |
| 制品落盘 `artifacts/<project>/<task>/<run>/` | 没做，报告只存路径 | 跟"worker 真干活"一起 |
| Router 常驻会话 | 没做，每次拆卡起一个会话 | 跟 Router 的记忆一起 |
| dsh profile `tina-node` | 没做，用 `sdk-minimal` 加进程外适配 | H1 换成插件时 |

原因是范围表和验收标准没对齐：验收测"闭环通不通"，范围表写"要建哪些零件"。H0 按前者合格，按后者没建全。**H1 写范围表时，每一项都要能指出它在哪条验收上被检查过。**

## 四、H0 没做到、但值得记下来的

1. **节点运行时没上 Effect。** vision 3.3 ① 选了它，H0 用的是普通 async。不是推翻，是延后：H0 的取消只有"关进程"一条，Effect 的收益在这里体现不出来。什么时候真需要"取消穿透到子进程和网络流"，什么时候再换。
2. **控制面不存任务（D58）。** 节点离线时看板是空的。第 3 节说的"摘要索引"推后。
3. **"对话"视图没做。** 它要存引擎转录，而 H0 明确不把原生事件落库。v1 再谈。
4. **报告兜底会掩盖失败。** Run 失败时节点补一份 `generated=1` 的报告，卡片进评审中。这是有意的——失败应该被人看见，而不是悄悄退回待办；但"一眼看出这是兜底"只靠一个布尔字段，v1 要更醒目。
