# 版本号与发布

> 这份文档是规范，不是决策记录。改它不需要讨论，但改完要在决策记录里记一笔。

## 一句话

产品版本用 SemVer，里程碑用 `H` 前缀，文档用「修订 N」。三者各管各的，不互相替代。

## 产品版本

格式：`MAJOR.MINOR.PATCH[-预发布][+构建]`

| 段 | 什么时候加 | 例子 |
|---|---|---|
| **MAJOR** | 破坏用户可感知的契约：控制面协议不兼容、数据迁移不可回滚 | `1.0.0` → `2.0.0` |
| **MINOR** | 加功能，向后兼容 | `1.1.0` → `1.2.0` |
| **PATCH** | 修 bug，不改行为 | `1.2.0` → `1.2.1` |
| **-预发布** | 未完成的版本 | `0.1.0-dev.3`、`0.1.0-rc.1` |
| **+构建** | 排查用，不参与排序 | `1.0.0+git.abc1234` |

规则：

- **对外第一个版本是 `1.0.0`。** `0.x` 的含义是"随时会变，别依赖它"。
- **预发布链条**：`0.1.0-dev.N` → `0.1.0-rc.N` → `0.1.0`。SemVer 的排序保证 `dev < rc < 正式版`。
- `dev.N` 每次合入主干递增；`rc.N` 只修 bug，不再加功能。
- **tag 格式** `v0.1.0`（带 `v`，git 惯例）。比较和展示时去掉 `v`。
- **版本号必须能从两处读到**：控制面 `GET /health`、Web 页脚。排查时第一个问题就是"你装的是哪版"。
- 构建信息不进 `MAJOR.MINOR.PATCH`，只进 `+` 之后的部分。

## 里程碑

`H0`、`H1`… 只在开发计划里用，**不进产品版本号**。

| 里程碑 | 产出 | 含义 |
|---|---|---|
| H0 | `0.1.0` | 单机跑通闭环的脚手架；打 tag 留档，不对外 |
| H1 | `1.0.0` | 第一个对外发布的版本 |

## 文档

不用版本号，用 **`修订 N · YYYY-MM-DD`**。

理由：产品已经有 `v1`，文档再叫 `v4`，两个 `v` 会混。文档的演化有 git，不需要再编码一遍。

## 不做什么

| 不做 | 理由 |
|---|---|
| 日历版本（`2026.11`） | 我们是可本地部署的，用户问的是"要不要升级"，不是"哪天发的" |
| 把 git sha 塞进 `MAJOR.MINOR.PATCH` | 破坏排序语义；放 `+` 里 |
| 每个 commit 打 tag | 只有里程碑和发布打 tag |
| 在 `1.0.0` 之前承诺兼容性 | `0.x` 就是"会变"的意思 |

## H0 阶段的发布动作

H0 不对外发布，只在自己机器上跑。流程简化成：

1. 合入主干 → CI 产出 `0.1.0-dev.N`，制品不进分发渠道
2. 功能冻结 → 打 `v0.1.0-rc.1`
3. 验收通过（见 `h0.md` 的验收标准）→ 打 `v0.1.0`
