# H0 实现规格

> 这是里程碑 H0 的规格，不是北极星。目标产物是 `0.1.0`。
> 产品为什么长这样见 [vision.md](vision.md)；本文只回答"这一版写什么、怎么算完成"。
> 本文与 vision 冲突时，以本文为准，并回头修 vision。

## 1. 目的

**证明四个组件能串成一条闭环，并把接缝撞出来。**

H0 验收的是架构假设，不是用户价值。它成功不看"功能多不多"，看两个问题有没有答案：

- vision 3.5 的待验证项，H0 之后还剩几个没答？
- 引擎端口的协议，H0 之后要不要推倒重来？

## 2. 验收

四条，缺一不可。

| # | 动作 | 通过标志 |
|---|---|---|
| 1 | `tina up` | 一条命令起全栈；打开 `http://localhost:7801` 能看到两个项目的看板；关掉节点，界面显示离线 |
| 2 | `demo.sh` | 从空库跑到"卡片进已完成"，每一步状态打在终端上 |
| 3 | `make verify` | 离线跑通：类型检查 + 单元测试 + e2e（真控制面 + 真节点 + fake engine）。不访问网络，不调用真实模型 |
| 4 | 手工 demo | 用真 dsh 跑一次同样的闭环，成功 |

另外留一份记录（写在 `docs/h0-report.md`，实现完成时补）：三个待验证问题的答案。

## 3. 范围

### 做

| 组件 | H0 里的样子 |
|---|---|
| **控制面**（Go） | 单二进制 `:7801`；本地单账号；节点注册与心跳；项目→节点目录；WS 入口与转发；摘要索引；`/health` 返回版本 |
| **节点运行时**（TS + Effect） | 注册到控制面；托管两个项目；SQLite + 文件；事件收件箱；调度；引擎端口客户端；报告兜底 |
| **引擎端口** | JSON-RPC over loopback TCP + 一次性令牌（见 4） |
| **fake engine** | 按脚本回放事件的假引擎，实现同一套端口协议 |
| **dsh bridge** | dsh profile `tina-node`，实现 create/send/subscribe/interrupt/respond/close/capabilities |
| **Router** | 端口上的一个常驻会话；固定 prompt；输出计划 JSON |
| **Worker** | 任务级会话；交结构化报告 |
| **Web** | 四列看板、卡片详情（对话 / Run / 报告）、待批面板 |

### 不做

多租户、组织与角色、SSO、多节点放置、NAT 穿透、对象存储、Postgres、移动端、桌面打包、执行隔离 / 沙箱、GitHub 接入、Router 记忆、跨项目计划、`fork`。

### 故意简化

| 简化 | 还债时机 |
|---|---|
| Router 用固定 prompt，不读项目约定 | v1 |
| Router 首审 = 固定检查：报告字段齐全 + 制品非空 | v1 换成真评审 |
| 重启后不自动恢复；运行中的 Run 标 `failed`，原因 `node_restart` | v1 |
| 事件快路径只实现系统默认规则（去重、每小时上限、自触发抑制的简化版） | v1 |
| 单节点、单用户、两个项目 | v1 加成员与多节点 |
| 一个 agent 绑一个节点 | 视需要 |

## 4. 进程与拓扑

```
浏览器 ──HTTP/WS──▶ 控制面 :7801
                      ▲
                      │ WS（节点主动连入）
                      │
                   节点运行时（单进程，托管 2 个项目）
                      │ JSON-RPC over loopback TCP
                      ▼
                   引擎（fake 或 dsh 子进程）
```

**H0 的 IPC 决定**：引擎端口用 `127.0.0.1` 上的随机端口 + 一次性令牌，不用 unix socket / 命名管道。

理由：H0 要在 Windows 上开发，Windows 没有 unix socket。vision 2.8 说的"本地 socket 上的 JSON-RPC"，H0 用 TCP 实现同一个协议；将来若要换传输，只改端口实现。

## 5. 引擎端口 v0

传输：TCP loopback；每行一个 JSON 对象（NDJSON）；首行握手带令牌。

| 方法 | 参数 | 返回 | H0 |
|---|---|---|---|
| `createSession` | `{profile, cwd, model, systemPrompt}` | `{sessionId}` | ✅ |
| `send` | `{sessionId, input}` | `{receipt}` | ✅ |
| `interrupt` | `{sessionId}` | `{ok}` | ✅ |
| `respond` | `{sessionId, requestId, answer}` | `{ok}` | ✅（dsh 侧可空实现） |
| `subscribe` | `{cursor}` | 事件流 | ✅ |
| `close` | `{sessionId}` | `{ok}` | ✅ |
| `capabilities` | — | `{interrupt, respond, fork, resume}` | ✅ |
| `fork` | `{sessionId, at}` | `{sessionId}` | ❌ |

事件格式：

```json
{"seq": 42, "sessionId": "...", "type": "tool.call", "ts": "2026-11-06T12:00:00Z", "payload": {}}
```

事件类型：`message.delta`、`message.end`、`tool.call`、`tool.result`、`approval.request`、`question`、`status`、`usage`、`turn.end`、`error`。

**fake engine 契约**：读场景文件（YAML），按 `input` 里的标记匹配，回放一组带固定 `seq` 的事件。同一输入必须产生同一输出——这是 `make verify` 能用它写断言的前提。

## 6. 数据模型

控制面（SQLite，单文件）：

| 表 | 关键列 |
|---|---|
| `account` | `id, name, created_at`（H0 只有一行） |
| `node` | `id, name, owner_id, status, last_seen_at, capabilities_json` |
| `project` | `id, name, home_node_id, created_at` |
| `project_index` | `project_id, task_id, title, status, assignee, needs_human, rev, updated_at` |

节点（SQLite + 本地文件）：

| 表 | 关键列 |
|---|---|
| `task` | `id, project_id, title, description, status, assignee_kind, assignee_id, deps_json, manual_override, created_at, updated_at` |
| `run` | `id, task_id, agent_id, node_id, originator_id, state, started_at, ended_at, error` |
| `report` | `id, run_id, state, summary, decisions_json, artifacts_json, blockers_json, usage_json, generated` |
| `approval` | `id, project_id, task_id, kind(plan/final), state, payload_json, requested_at, decided_at, decided_by` |
| `event` | `id, project_id, seq, type, actor, payload_json, created_at`（append-only） |

制品落盘：`artifacts/<project>/<task>/<run>/`。

## 7. 状态机

**Run**

```
queued → dispatched → running → completed
                            ↘ failed / cancelled
```

进入 `running` 后节点重启 → `failed`，`error=node_restart`。

**计划**

```
pending → approved / rejected
```

计划被批准后才创建 Task。

**卡片状态**（从 Run 与报告推导，D23）

| 卡片状态 | 条件 |
|---|---|
| 待办 | 没有活跃 Run，且计划已批 |
| 进行中 | 存在 `queued` / `dispatched` / `running` 的 Run |
| 评审中 | 存在 `completed` 的 Run 且报告已落库，等人终审 |
| 已完成 | 人终审通过 |

**人工覆盖**：人一旦手动改状态，`manual_override=1`，此后不再推导。

**报告兜底**：Run 以 `failed` / `cancelled` 结束且没有报告时，运行时从事件流生成一份，`generated=1`。

## 8. 里程碑

按顺序做，前一个的完成标志没达到不开下一个。

| # | 里程碑 | 做什么 | 完成标志 |
|---|---|---|---|
| **M0.1** | bridge spike | 用真 dsh 起会话、发一句、读事件流、调用 `interrupt` | 脚本跑通；记录 `interrupt` 是"优雅中断"还是"只能杀进程"，以及 `fork` 能不能做 |
| **M0.2** | 端口 + fake engine | 按第 5 节实现协议；fake engine 能按场景回放 | 端口契约测试逐方法通过；同一输入两次运行事件序列完全一致 |
| **M0.3** | 骨架 | `tina up` 起控制面与节点；节点注册；Web 显示两个空看板 | 一条命令起全栈；杀掉节点后控制面 3 秒内显示离线 |
| **M0.4** | 闭环 | 建卡 → Router 拆卡 → 批计划 → 派 worker（fake）→ 收报告 → 评审中 → 人终审 | `demo.sh` 跑通；数据库状态与第 7 节逐条对上 |
| **M0.5** | UI + 验收 | 三个视图；`make verify` 进 CI；真 dsh 手工验收 | 第 2 节四条全过 |

依赖：M0.1 → M0.2；M0.2 + M0.3 → M0.4 → M0.5。

## 9. 风险

| 风险 | 影响 | 应对 |
|---|---|---|
| dsh 只能杀进程，没有优雅中断 | 端口要拆成 `interrupt` / `kill`，节点要处理"被中断的会话还能不能读事件" | M0.1 先验；结论直接改第 5 节的表 |
| Effect 与子进程 / 流集成比预期难 | M0.3 工期 | M0.2 里顺带做一个最小 spike：起进程 → 读流 → 取消 |
| 事件量大时 SQLite 写竞争 | 单写者模型的前提 | H0 量小，先按单写者写；压测放 v1 |
| fake engine 与真 dsh 行为差异大 | 闭环在 CI 绿、手动手却挂 | 手工 demo 是验收的一部分，不是可选项 |

## 10. H0 期间要定的事

不阻塞开工，但要在对应里程碑前定下来：

| 要定 | 定它的时间点 |
|---|---|
| Router 计划 JSON 的字段（拆哪些卡、派给谁、验收标准） | M0.4 开始前 |
| 报告自动生成的判定口径（多久没交算超时） | M0.4 开始前 |
| 待批面板放在首页还是看板内 | M0.5 开始前 |
