# M0.1 bridge spike：dsh 的会话生命周期

> 提议中 · 2026-11-06 · 证据来自本机一次性脚本（未入库）
> 结论已记进决策记录 D48–D51；`docs/h0.md` 第 5 节按本文改。

## 为什么先做这个

端口协议是 H0 剩下的所有东西的地基，而它假设 dsh 能干四件事：建会话、发消息、读事件流、**中断**。前三个从文档看没问题；第四个，文档里写着"客户端放弃轮次的方式是关闭运行时进程"。如果真是这样，端口的方法表和"Router 是个常驻会话"这个写法都要动。

## 怎么测的

真 dsh，`sdk-minimal` profile（不叠加 `dsh-base` 的完整最小树：一个模型适配器、一个持久化目录、一个 pwsh 工具、`danger-full-access`），隔离的 `DSH_HOME`，管道 stdio，按 `dsh-sdk-protocol` 的 JSON-RPC 收发。四个场景：

| 场景 | 做什么 |
|---|---|
| A | 建会话 → 派活 → 工具执行中**硬杀进程** → 重启 `session/resume` |
| B | 建会话 → 派活 → 工具执行中**协议 `shutdown`** → 重启 `session/resume` |
| C | 普通一轮跑完，量"这轮结束了"的信号 |
| D | 4 个进程共用一个 `DSH_HOME` 并发跑 |

## 结果

### 1. 协议里没有"停"

`session/interrupt`、`session/cancel`、`session/close`、`session/fork`、`session/list` 五个方法全部返回 `-32603 unknown method`。整套协议只有七个方法：

```
initialize  session/prompt  session/resume  session/wait
session/working-directory/get  session/working-directory/set  shutdown
```

`shutdown` 不带参数，作用于整个进程。停一轮的办法只有两个：关进程，或者让**进程内的插件**调 `agent.cancel({kind:'user'})`——dsh 自己的"用户停止"就走这条，但没接在协议上。

### 2. `shutdown` 是优雅的，只是它带走整个进程

工具执行中发 `shutdown`：193ms 后退出码 0，盘上补齐三条

```
tool/result   error.code = ABORTED
step/end
turn/end      reason = {kind:'aborted', reason:{kind:'disposed'}}
```

### 3. 硬杀也能恢复，靠的是下次 `resume`

工具执行中硬杀：12ms 退出（signal `SIGKILL`），日志停在 `tool/call`。下次 `session/resume` 成功，并补上合成的三条

```
tool/result   error.code = TOOL_OUTCOME_UNKNOWN
              "The tool call was interrupted after it was recorded, but no result
               was durably recorded. Its outcome is unknown. Decide whether to
               retry from the tool semantics: retry only if the operation is
               read-only or idempotent; if it may have side effects, first verify
               external state or ask the user. Do not retry blindly."
step/end
turn/end      reason = {kind:'interrupted'}
```

修复发生在 **resume 那一刻**，不是崩溃那一刻。所以"被杀之后会话是什么状态"这个问题，只有在 resume 之后才有答案。

### 4. 工具子进程不随引擎死

硬杀前后各查一次进程表，跑着 `Start-Sleep -Seconds 25` 的 pwsh 还在。引擎死了，它的工具孙子还在跑——收尸是节点的责任。

### 5. 一轮结束只有一个可靠信号

`turn/end` 事件的 `data.reason.kind`：`completed` / `interrupted` / `aborted`。`session.status` 的 running→idle 和它落在同一毫秒，是等价的第二个信号；`session/wait` 只是"等到空闲"，普通一轮 1ms 就返回，对单个 Run 没有区分度。

### 6. 事件词汇长这样，映射表要盖住它

一轮完整的原生序列：

```
turn/start → step/start → user/message → request/header → request/context
→ assistant/message → tool/call → tool/result → step/end → turn/end
```

外加快照类（`system/message`、`session/title`）和旁路事件（`agent/inbox/spliced`、`session-log-deepseek/delivery-accepted`、`session/end-seed`）。信封是 `{type, seq, time, data}`，`seq` 单调递增。`assistant/message` 带着完整 stream 记录，一个 step 约 5–6KB。

端口不照抄这些名字（vision 2.8：不把引擎原生类型泄漏到产品侧）。实测的作用是告诉我们**映射表要盖住哪些原生事件、哪些可以直接扔**——`step/*`、`request/*`、`system/message` 和 stream 记录都可以扔，真正要翻译的只有 `turn/start`、`turn/end`、`user/message`、`assistant/message`、`tool/call`、`tool/result` 六种。

### 7. 多进程共用一个 `DSH_HOME` 没问题

4 个进程并发 `initialize`：2.5s（单进程 1.8s，基本线性）。4 个会话并发各跑一轮：879ms。

## 这些数字改了端口什么

| 端口方法 | 原计划 | 现在怎么写 |
|---|---|---|
| `createSession` | 一个引擎托管多个会话 | **拉起一个 dsh 子进程**；端口实例与会话一比一 |
| `send` | — | `session/prompt`；进程不在就先 `initialize` + `session/resume` |
| `interrupt` | 优雅中断 | `shutdown`，2 秒不退再杀 |
| `close` | 关闭会话 | 同 `interrupt` |
| `subscribe` | `{cursor}` 拉事件 | 推实时事件；dsh 不重发历史，断线补偿归节点自己的事件表 |
| `respond` | dsh 侧可空实现 | 确实是空的：协议里没有 server→client 请求 |
| `capabilities` | 运行时查询 | 静态：`{interrupt: true, respond: false, fork: false, resume: true}` |
| `fork` | H0 不做 | 仍然不做；将来只能靠插件，不靠协议 |

三条落到节点身上的账：

1. 每次 `interrupt` 或崩溃之后，下一次 `send` 要付一次 `initialize`（约 1.8s）。
2. 工具子进程要自己收。
3. 事件要投影，不能原样入库。

## 还留着没答的

- 进程内 `agent.cancel({kind:'user'})` 存在，所以**写一个 dsh 插件就能给会话补上 `session/interrupt`**。H0 不写；要不要写看 H0 里 Router 被中断的频率——如果 Router 几乎不被打断，进程级中断就够了。
- 并发上限没压。4 个进程不是上限，20 个没测。
- 多个 dsh 进程共用 `DSH_HOME` 时，`settings` 与 `storages` 的并发写没验证；H0 里节点只写会话目录。
